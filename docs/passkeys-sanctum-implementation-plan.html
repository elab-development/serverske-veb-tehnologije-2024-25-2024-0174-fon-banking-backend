Tehnički plan

Laravel Passkeys sa Sanctum bearer autentifikacijom

Zadržavamo bezbednu WebAuthn implementaciju paketa, uklanjamo njegov session sloj i uvodimo API tok koji odgovara postojećoj aktivaciji uređaja, PIN-u i Sanctum tokenima.

Backend koraci 1-17 završeni Laravel 13 laravel/passkeys 0.2.1 Sanctum bearer tokens Trusted devices

Ciljna arhitektura

Status implementacijeBackend passkey i Sanctum tok je završen: bezbedan PIN enrollment, stateless WebAuthn ceremonije, login, registracija, upravljanje credentialima, token politika i kriptografski integration test.

Zadržavamo

  • Paketove WebAuthn akcije i serializer.
  • Postojeću passkeys tabelu i User trait.
  • Aktivaciju uređaja i PIN kao bootstrap/fallback.
  • Sanctum bearer tokene za API pristup.
  • Pravilo da login zahteva pouzdan uređaj.

Ne koristimo

  • Automatske paketove rute i kontrolere.
  • web guard i browser session.
  • password.confirm middleware.
  • Request klase koje challenge čitaju iz sesije.
  • Kopiranje ili menjanje fajlova u vendor/.

Registracija

Aktivacija + PIN
  → Sanctum token
  → PIN confirmation grant
  → registration options
  → WebAuthn credential
  → StorePasskey

Prijava

Pouzdan uređaj
  → verification options
  → WebAuthn assertion
  → VerifyPasskey
  → Sanctum token

1. Bezbednosni preduslovi (završeno)

Ne puštati passkey login pre ovih izmena. Slabiji PIN fallback i dalje može poništiti bezbednosnu korist passkeya.

Rate limiting i lockout (završeno)

OperacijaPočetni limitKljuč
Aktivacija5/minIP
Postavljanje PIN-a5/minIP + uređaj
PIN prijava5/minIP + uređaj
Potvrda PIN-a5/minkorisnik + IP
Passkey options10/minIP + uređaj
Passkey verification5/minIP + uređaj
Passkey management5/minkorisnik

Dodati i privremeni PIN lockout posle više grešaka. Četvorocifreni PIN ima samo 10.000 kombinacija.

Status korisnika (završeno)

Napraviti EnsureUserIsActive middleware i zahtevati status === 'active' na PIN loginu, passkey rutama i bankarskim rutama. Kada korisnik postane blokiran, izvršiti:

$user->tokens()->delete();

Prvi PIN (završeno)

Aktivacija treba da izda jednokratni server-side enrollment token vezan za korisnika i uređaj. POST /set_pin mora trošiti taj token, umesto da veruje samo device_identifier vrednosti.

2. Isključivanje paketovih ruta (završeno)

U AppServiceProvider::register(), pre nego što Laravel bootuje paketov provider:

public function register(): void
{
    Passkeys::ignoreRoutes();

    Passkeys::useUserModel(User::class);
    Passkeys::usePasskeyModel(Passkey::class);
}

Provera:

php artisan route:list --path=passkeys -v

Root rute /passkeys/login, /passkeys/confirm i /user/passkeys više ne smeju postojati.

3. Konfiguracija (završeno)

PASSKEYS_RELYING_PARTY_ID=fon-banking.duckdns.org
PASSKEYS_ALLOWED_ORIGINS=https://fon-banking.duckdns.org
PASSKEYS_USER_HANDLE_SECRET=<stabilan-slucajan-secret>
PASSKEYS_CEREMONY_TTL=120
  • RP ID i allowed origins moraju odgovarati stvarnom WebAuthn klijentu.
  • Produkcija mora koristiti HTTPS.
  • User handle secret se ne menja nakon prve registracije.
  • Challenge traje 60-120 sekundi.

4. User model (završeno)

Zadržati PasskeyUser i PasskeyAuthenticatable. Dodati čitljivo ime za sistemski credential picker:

public function getPasskeyDisplayName(): string
{
    return "{$this->first_name} {$this->last_name}";
}

Username može ostati email adresa.

5. Server-side ceremony store (završeno)

Napraviti app/Services/PasskeyCeremonyStore.php. Klijent dobija samo slučajni ceremony_id, dok serialized options ostaju na serveru.

Login payload

{
  "type": "login",
  "options": "{json}",
  "user_id": 123,
  "device_id": 45,
  "access_token_id": null
}

Registration payload

{
  "type": "registration",
  "options": "{json}",
  "user_id": 123,
  "device_id": null,
  "access_token_id": 789
}

Jednokratna potrošnja

  1. Zaključati ID pomoću Cache::lock(...).
  2. Učitati i proveriti payload/type.
  3. Obrisati payload pre WebAuthn provere.
  4. Otpustiti lock i vratiti payload.
Replay zaštitaI neuspešan credential pokušaj troši ceremoniju. Klijent zatim mora tražiti nove options.

6. PIN potvrda za management (završeno)

POST /api/v1/auth/confirm-pin posle uspeha vraća jednokratni grant:

{
  "status": "success",
  "confirmation_token": "opaque-random-token",
  "expires_in": 300
}

Server-side grant sadrži user_id, ID trenutnog Sanctum tokena i purpose passkeys.manage. Važi do pet minuta i koristi se samo jednom.

Javne

8. Login options (završeno)

POST /api/v1/auth/passkeys/login/options

{
  "device_identifier": "device-id"
}
  1. Validirati i pronaći uređaj.
  2. Proveriti is_trusted i aktivan status korisnika.
  3. Proveriti da korisnik ima passkey.
  4. Pozvati GenerateVerificationOptions($user).
  5. Options sačuvati uz user/device binding.
  6. Vratiti ceremony_id i WebAuthn::toBrowserArray($options).

Javni response za nepoznat uređaj, blokiran nalog ili nedostajući passkey mora biti generički.

9. Login verification (završeno)

POST /api/v1/auth/passkeys/login

{
  "ceremony_id": "...",
  "device_identifier": "device-id",
  "credential": {
    "id": "...",
    "rawId": "...",
    "type": "public-key",
    "response": {}
  }
}
  1. Parsirati credential sa WebAuthn::fromJson.
  2. Atomski potrošiti login ceremoniju.
  3. Proveriti vezani uređaj, trust i status korisnika ponovo.
  4. Deserijalizovati sačuvane request options.
  5. Pozvati VerifyPasskey($credential, $options, $user).
  6. Ažurirati device.last_login_at.
  7. Izdati Sanctum token i vratiti postojeći login response format.
Ownership provera$user se obavezno prosleđuje u VerifyPasskey, čime se credential vezuje za očekivanog korisnika.

10. Registration options (završeno)

POST /api/v1/passkeys/registration/options

{ "confirmation_token": "..." }
  1. Učitati korisnika i trenutni Sanctum token.
  2. Potrošiti confirmation grant.
  3. Proveriti user ID, access token ID i purpose.
  4. Pozvati GenerateRegistrationOptions($user).
  5. Sačuvati registration ceremoniju vezanu za korisnika i token.
  6. Vratiti ceremony_id i options.

11. Završetak registracije (završeno)

POST /api/v1/passkeys

{
  "ceremony_id": "...",
  "name": "Moj telefon",
  "credential": {
    "id": "...",
    "rawId": "...",
    "type": "public-key",
    "response": {}
  }
}
  1. Validirati naziv i parsirati credential.
  2. Potrošiti registration ceremoniju.
  3. Proveriti korisnika i trenutni Sanctum token.
  4. Pozvati StorePasskey($user, $name, $credential, $options).
  5. Vratiti 201 Created bez credential JSON-a.

12. Lista passkeyeva (završeno)

GET /api/v1/passkeys uvek čita $request->user()->passkeys(). Vraća samo:

  • id
  • name
  • last_used_at
  • created_at

Klijent nikada ne šalje user_id, a credential JSON se ne izlaže.

13. Brisanje passkeya (završeno)

DELETE /api/v1/passkeys/{passkey}

{ "confirmation_token": "..." }
  1. Potrošiti management confirmation grant.
  2. Proveriti korisnika i trenutni token.
  3. Učitati passkey kroz relaciju autentifikovanog korisnika.
  4. Pozvati paketov DeletePasskey.
  5. Vratiti 204 No Content.

Poslednji passkey može biti obrisan jer PIN ostaje fallback.

14. Form Request klase (završeno)

PasskeyLoginOptionsRequest
PasskeyLoginRequest
PasskeyRegistrationOptionsRequest
StorePasskeyRequest
DeletePasskeyRequest

One validiraju request i parsiraju credential preko WebAuthn::fromJson. Ne koriste paketove Request klase jer one pozivaju $this->session()->pull(...). Ceremony i poslovna autorizacija ostaju van Request klasa.

15. Sanctum token politika (završeno)

Minimalno kompatibilno izdavanje:

$user->createToken($device->device_identifier)->plainTextToken;

Preporučeno je obrisati prethodni token istog uređaja, koristiti čitljivo ime uređaja i uvesti expiration. Ako se politika menja, zajedničku logiku izdvojiti u DeviceTokenIssuer koji koriste PIN i passkey login.

17. Testovi (završeno)

Dodati:

tests/Unit/PasskeyCeremonyStoreTest.php
tests/Feature/PasskeyAuthenticationTest.php
tests/Feature/PasskeyManagementTest.php

Ceremony store

  • TTL, replay i type binding.
  • Atomska paralelna potrošnja.
  • JSON payload uz serializable_classes=false.

Login

  • Trust/status provere u oba koraka.
  • Credential ownership i ceremony/device binding.
  • Sanctum token radi na bankarskoj ruti, bez web sesije.
  • last_used_at i last_login_at se ažuriraju.

Management

  • Sanctum i confirmation grant su obavezni.
  • Grant i ceremonija su jednokratni i token-bound.
  • Tuđi passkey se ne može listati ni obrisati.
  • Credential JSON se ne vraća.
Integration fixtureKontrolerske testove je moguće mockovati, ali najmanje jedan test treba da koristi stvaran WebAuthn fixture radi provere formata i paketove validacije.

19. Završna verifikacija

php artisan route:list --path=passkeys -v
vendor/bin/pint --test
composer test
composer audit --locked
  • Nema paketovih root-level web ruta.
  • Management koristi auth:sanctum.
  • Passkey tok ne koristi Laravel session.
  • Uspešan login vraća Sanctum bearer token.
  • Challenge je server-side, kratkotrajan i jednokratan.
  • Login je vezan za pouzdan uređaj i pravog korisnika.
  • Blokiran korisnik ne dobija niti koristi token.
  • Management zahteva nedavnu PIN potvrdu.
  • Nijedan vendor/ fajl nije izmenjen.
Kasniji Expo korakexpo-local-authentication nije WebAuthn/passkey implementacija. Nativni klijent mora vratiti standardni credential JSON i zahtevaće odgovarajući passkey modul, iOS associated domains i Android Digital Asset Links.
